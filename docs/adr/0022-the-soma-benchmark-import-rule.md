# The `soma.benchmark` import rule

Extends [ADR 0010](0010-project-protocols-live-outside-the-installable-core.md). The Built-in Benchmarks ship in the soma wheel as one package, `soma.benchmark`, that sits above the core: it imports the core's public modules, and the core never imports it. `import soma` does not load it. Importing it registers its components, the way a user package does, and the `soma` command imports it at startup. Four import-linter contracts in `pyproject.toml` enforce the rule, and CI runs `lint-imports` before the test suite.

## Why

ADR 0010 says what belongs in the core: a mechanism whose interface and synthetic tests need no dataset name, fixed cohort, fixed class count, known sample ids or publication policy. But the benchmark side was spread over four places (`soma.benchmarks`, `soma.curation`, `soma.leaderboard`, `soma.robustness`), and the core loaded it anyway. The aggregator, head, decoder and learner registries imported `soma.benchmarks` on the first lookup that missed, so a saved config could name a benchmark's private head without anyone importing the benchmark code. Nothing stopped core code from importing benchmark code, or benchmark code from importing private core modules. The detection harness kept a table of its three datasets and imported each dataset's scorer. One protocol borrowed a helper from another.

## Decisions

- **One package, one sub-package per protocol.** The root of `soma/benchmark/` holds the generic mechanism: `spec`, `registry`, `run`, `reproduction`, `leaderboard`, the manifest helpers (`curation`), segmentation coverage (`coverage`), point-annotation tiling (`tiles`), the detection harness (`detection`) and its attention probe (`attention`). Each protocol is one package (`eva`, `hest`, `ocelot`, `midog`, `monkey`, `croma`) holding its curator, its recipes, its scorer (MIDOG's F1 in `midog/`, FROC in `monkey/`, the CRoMa data preparation in `croma/`), its `reference.csv` and its `results.csv`. `reference/<name>.csv` and `results/<name>.csv` become `<name>/reference.csv` and `<name>/results.csv`. OCELOT's spacing-migration evidence, `ocelot/spacing-migration.csv`, is read through `results_root`.
- **Explicit import (option C).** `soma.benchmark` registers the benchmarks, and its private aggregators, heads, decoders and learners, when it is imported. The `benchmarks` registry is created inside it. From Python, `import soma.benchmark` first or name a component by its dotted path. The `bundled_module` lazy hook is deleted.
- **A registry announces its kind.** A `Registry` adds itself to a registry of kinds in `soma.registry` when it is built, one live registry per kind. `soma.components()` lists exactly the kinds whose module is imported. While `soma.benchmark` is not imported, `soma.components("benchmarks")` and a lookup of a benchmark-only name fail with an error that names `import soma.benchmark`.
- **The detection harness names no dataset.** `detection.py` keeps no dataset table and imports no scorer or curator. Each of `ocelot`, `midog` and `monkey` registers a `DatasetSpec` at import. The spec carries the dataset's committed config, its `curate` and its native `score` callable. `midog` and `monkey` also register their `detection/<dataset>` views. Datasets are listed in registration order, which `soma/benchmark/__init__.py` fixes as ocelot, midog, monkey, the report order. This is the only behaviour change in the move.
- **Four contracts.** (1) Layers: `soma.cli` over `soma.benchmark` over every other module of `soma`; the contract is exhaustive, so a new top-level module must be placed. (2) The six protocol packages are independent. (3) The `soma.benchmark` tree imports no `_`-prefixed module (`soma._internal` and the private modules of `extract.cache` and `testing`). (4) No core namespace but `soma.pipeline` and `soma.presets` imports `soma.config` or `soma.plan`: the verbs stay config-free. Contracts 3 and 4 check direct imports. A test keeps each contract's module list in step with the package. Import-linter sees modules, not names, so another test in `tests/repo/test_import_contracts.py` refuses a `_`-prefixed core name that the benchmark package imports from a public module.
- **A core gap is fixed in the core.** When a benchmark needed private code, a public route was added instead. The params helpers (`NoParams`, `check_positive` and the other checks) are importable from `soma.registry`. `soma.data.targets.resolve_point_classes` gives a detection head's class scheme. `locate_run_config` moved from OCELOT to the generic `soma.benchmark.registry`, so EVA no longer imports OCELOT.
- **The verbs' own types live beside the verbs.** `Component` is in `soma.registry`, `EncoderLeaf` in `soma.models.encoders`, `CacheOptions` in `soma.extract.cache.options` and `is_annotation_sampling` in `soma.extract.preprocessing`. `soma.config` holds them and still exports them. `resolve_pipeline_preprocessing` and `resolve_pipeline_dense` read a config or a plan, so they moved to `soma.pipeline.extraction`.

## Considered and rejected

- **Keep the lazy hook.** A saved config would still load without the import, but the core would keep importing the benchmark package at run time, which no static contract can see. Users would also have two ways a component gets registered.
- **Entry points.** They stay a later option for when a real third-party plugin appears. For the one in-tree package, an explicit import is enough.
- **Two distributions.** Core and benchmarks move in lockstep under one version, and the benchmarks are the regression oracle for core changes. The import rule can be kept when the package is split later.
- **Exempt `soma.extract` from contract 4.** The verb would keep importing the config module whose sections mirror it, and the contract would no longer say "the verbs stay config-free". The presets are exempt because building an `ExperimentConfig` is all they do.

## Consequences

- From Python, a saved benchmark config or a bundle trained with a benchmark's private head needs `import soma.benchmark` before it is loaded. The `soma` command needs nothing.
- `soma reproduce`, `soma leaderboard` and `soma list benchmarks` behave as before. The eleven pinned benchmark plans, the reference rows and the ledgers are unchanged apart from their paths.
- `soma.config.CacheOptions`, `soma.config.Component` and `soma.config.EncoderLeaf` still resolve, so pickles and bundles that name them still load.
- `prepare_croma` keeps recording its tool as `soma.robustness.prepare_croma`. This name is an identifier in the provenance of prepared PathoROB trees on disk, not an import path, and changing it would reject every prepared tree.
